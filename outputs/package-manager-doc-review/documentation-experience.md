## RuyiSDK 文档整理与重构实践经验分享

这段时间我主要参与了 RuyiSDK 包管理器文档的整理和重构。过程中经历了问题梳理、目录调整、正文修改和多轮 review，也遇到了一些理解和协作上的问题。

下面结合具体经历，分享一些对我比较有帮助的做法，供大家开展文档任务时参考

### 1.开始前

#### (1)明确目标、读者和交付形式

- 文档写给谁看，要帮助他们完成什么

- 本次需要解决哪些问题，修改范围是什么

- 在哪里讨论和审核，最终以什么形式交付

#### （2）明确“重构"

重构的核心是解决表达逻辑方面的问题，需要按照用户的使用步骤，把相关信息串起来。

例如，包管理器文档要区分管理软件包、配置开发环境、为设备安装系统等任务；应用开发又需要交代准备环境、获取源码、构建和运行之间的关系。这些分别存在，并不代表读者能够顺利完成整个过程。

比较适合我的做法：先列出整体结构和每章要解决的问题，确认后再写一个代表性章节，作为后续整理的参考。

#### （3）注意区分内部沟通与面向用户的正式说明

公开文档是项目对用户、开发者和贡献者说的话。

整理会议记录或聊天内容时，注意先区分：

- 产品事实：核实后可以进入正文。

- 面向用户的操作建议：整理成完整、清楚的说明。

- 内部安排和临时注意事项：留在任务记录或协作沟通中。

### 2.关于协作

- 初稿统一使用飞书原生文档，通过修订和评论讨论，定稿后再导出 Markdown，经审查确认后再提交PR。

- 对较多、较细的问题，也可以集中开会逐段检查，减少来回解释。

- 收到 review 后，理解原因，检查其他位置是否存在同类问题。

- 理解不确定时，及时确认。

交付前可集中检查的细节：

- 目录、文件名和显示标题是否对应，必要时先提供本地结构给老师确认。

- 导出后的表格、代码块、图片和链接是否正常。

- 暂未创建的目标文档，在草稿中统一标记“链接待补充”，后续全文搜索补齐；提交前说明尚未完成的依赖。

- 按贡献指南运行格式检查，查看 diff，排除无关修改。

- 确认基于正确分支提交，并在 PR 中写清问题、改动和验证情况。

### 2.重构中注意事项

#### （1）按照用户第一次操作的过程检查文档。

学生也是 RuyiSDK 的重要用户群体，我们自己初次接触时的疑问很有参考价值。因此，遇到不明白的地方，可以先记录下来，判断文档是否缺少必要说明。

写操作步骤时，我主要重点检查以下四部分是否通畅：

前提是否明确、命令如何执行、结果怎样判断、失败后去哪里查。

例如：

- 软件源配置需要形成“查看当前状态—按需修改—确认结果—更新索引”的顺序。默认配置已经满足需求时，也要说明可以继续，避免读者机械执行所有命令。

- 检查构建产物时，若只写“应能识别为案例预期的 RISC-V 程序”不够明确，补充`file` 命令的输出示例，并解释需要关注的字段，读者才有可以对照的依据。

- 终端截图改成代码块时，也应保留必要回显，而不只是提取命令。

#### (2) 主流程保持简洁，详细信息放在需要的位置。

先介绍直接、常用的设置方法，再安排特殊情况。

例如：遥测的三种模式应平等列出，说明按需选择对应命令；环境变量等补充内容可以放在详细章节。可选功能也要明确标注，不要写得像必做步骤。

整理时，可以让不同内容各自承担明确作用：

- 入门导航说明操作顺序和章节入口。

- 常用命令速查方便快速查阅。

- 任务章节讲清完整流程。

- 命令详解按子命令介绍选项和用例。

- 问题排查提供检查方法、处理入口和求助渠道。

命令详解可配合具体示例，尤其是仅看参数名称不容易理解的用法，让读者知道什么时候用、怎么组合使用。

#### **（3）关于AI协作**

首先，真实性是首要，涉及到命令、参数时一定注意不可让AI的任何行为代替人工验证。另外，面向用户的文档最重要的是与产品功能一致，而非杜撰或美化。

目前我探索出比较合适的与AI协作的流程：

a）人工明确思路和大纲

b）AI跑一遍项目文档、Ruyi 和 packages-index 等相关源码，据此填充细节。（注意完整阅读，多轮探讨）另注意区分：“查过帮助”“核对过源码”和“实际运行过”，不可它说什么就是什么。

c）人工复合命令和参数

d）修改格式、语气，增改相关细节

e）再让AI整体review一遍，给建议，改不改、怎么改人工决定。

其次，强大的AI总是喜欢让它的每一句话无懈可击，确实挑不出错，但也牺牲了可读性，文档不会因为每一个小众的点都面面俱到而变得好用好读。为避免让读者陷入阅读AI给出的长难句的困境：

- 喂给AI防止防御性写作的prompt

- 明确任务边界，避免盲目扩大范围

- 先用自己的话先大胆写，再给AI review, 据它给的建议复核、修改。开始比较麻烦，后续可把写好的完整章节再喂给AI学习。

- 主线只需明确大多数用户会遇到的问题并给出清晰的步骤和方案

#### （4）考虑后续维护，减少容易过时的信息。

文档需要随着产品持续更新，不宜把整篇说明绑定在某个固定版本上。

具体写法上，可注意：

- 下载入口引导到发布页，避免到处写死版本号。

- 文件名使用英文占位符，配合一个具体示例说明替换方法。

- 同一概念、命令和占位符保持统一。

- 发行版收录状态等易变信息保留查询入口。

- 只有版本差异确实影响操作时，才专门说明适用范围。
